# 10 · 角色卡格式与导入导出

> 适用版本：SillyTavern 1.19.0（第 6 节另含酒馆助手 4.9.5）｜ 核对日期：2026-09-17，第 6 节 2026-09-18 真实酒馆实测 ｜ 对应分区：拼装、规划·完善优化卡
>
> 核对来源：SillyTavern 源码 `src/endpoints/characters.js`（`convertWorldInfoToCharacterBook`）、`public/scripts/world-info.js`（`convertCharacterBook`、`newWorldInfoEntryDefinition`、`world_info_position`），以及角色卡 V3 规范。本篇只写与制卡有关的事实。

## 1 一张卡由哪些部分组成

一个角色卡 JSON 的顶层有两套字段：

- **V2 兼容镜像**：`name`、`description`、`personality`、`scenario`、`first_mes`、`mes_example`、`tags` 等，酒馆写卡时会跟着 `data` 一起刷新。
- **`data`**：真正读的数据。除上面这些外还有 `alternate_greetings`、`group_only_greetings`、`system_prompt`、`post_history_instructions`、`creator`、`creator_notes`、`character_version`、`character_book`、`extensions`。

V3 卡的标记是 `spec: "chara_card_v3"`、`spec_version: "3.0"`。V2 卡是 `chara_card_v2`；更早的卡没有 `data`，顶层就是数据本身。Cardwright 三种都能导入，导出一律是 V3。

`data.extensions` 里与制卡有关的：

| 字段 | 内容 |
| --- | --- |
| `world` | 绑定的世界书名。卡内嵌世界书时，这里写同一个名字 |
| `regex_scripts` | 正则数组 |
| `tavern_helper` | `{ scripts: [], variables: {} }`，酒馆助手脚本放这里 |
| `depth_prompt` | `{ depth, prompt, role }` |

其他扩展字段（别的工具写进去的）不要删：Cardwright 会原样保留，导出时照原样写回。

## 2 世界书的三种形态

同一条世界书条目，在三个地方字段名不一样：

| 形态 | 结构 | 何时遇到 |
| --- | --- | --- |
| 独立世界书导出 | `{ entries: { "<uid>": { key, keysecondary, comment, content, constant, order, position, depth, disable, excludeRecursion, … } } }` | 单独导出/导入世界书文件 |
| 卡内 `character_book.entries[]` | `{ id, keys, secondary_keys, comment, content, constant, selective, insertion_order, enabled, position, use_regex, extensions }` | 卡 JSON 里 |
| 酒馆助手接口 | `{ name, enabled, strategy{type,keys,…}, position{type,role,depth,order}, content, … }` | 脚本、创角页写条目时 |

**组件文件用第一种**（独立世界书的字段名），因为它的字段最全、与导入导出一一对应。

### 卡内与独立之间的换算

- `id ↔ uid`、`keys ↔ key`、`secondary_keys ↔ keysecondary`、`insertion_order ↔ order`、`enabled ↔ !disable`。
- **真实插入位置以 `extensions.position` 为准**。卡内的 `position` 字符串只有 `before_char` 和 `after_char` 两种，@深度 条目在卡里写的是 `after_char`，而 `extensions.position` 是 4。只看字符串会把 @深度 条目错当成「角色定义后」。
- 卡内 `extensions` 里是一套蛇形命名的镜像字段：`exclude_recursion`、`prevent_recursion`、`display_index`、`scan_depth`、`match_whole_words`、`group_weight`、`use_group_scoring`、`automation_id`、`ignore_budget` 等，共 31 个。导出卡时酒馆会把它们全部补齐。
- 酒馆导出卡时固定写 `use_regex: true`；它把关键词当正则处理。
- 独立世界书里的 `addMemo`、`characterFilter` 在卡内没有对应字段，导出卡时不写。

### 酒馆自己的默认值

新建条目时酒馆填的默认值：`order: 100`、`position: 0`、`probability: 100`、`useProbability: true`、`depth: 4`、`groupWeight: 100`、`selective: true`、`selectiveLogic: 0`，以及一串 `null`（`scanDepth`、`caseSensitive`、`matchWholeWords`、`useGroupScoring`、`sticky`、`cooldown`、`delay`）。导入别的工具做的精简条目时，缺的字段按这套默认值补。

注意酒馆导出卡时有两处会把 `null` 压成 `false`（`use_group_scoring`、`useProbability`），Cardwright 导出时保留原值，语义不变。

## 3 uid 怎么分配

酒馆新建条目时用的是「最小空号」：删掉 3 号再建，新条目又叫 3 号。**Cardwright 不这样做**：世界书控制器按 uid 管理分歧组，复用 uid 会让旧存档指向另一条条目。所以：

- uid 由应用的计数器分配，只增不减，记在 `卡项目.json` 的 `nextUid` 里。
- 分区 AI 通过 `card_new_component` 取 uid，不自己编。
- 拼装检查会报错：uid 重复、uid 大于等于计数器（说明是手写的）。

导入别人的卡时，计数器直接跳到「最大 uid + 1」。原卡里缺号（例如 285–289 空着）不去填补。

## 4 组件文件

```
世界书/<分区>/<顺序>-<名称>.md     条目正文
世界书/<分区>/<顺序>-<名称>.json   条目参数（独立世界书字段名 + uid）
世界书/.cardwright-book.json       应用维护：世界书名、条目顺序、character_book 的额外字段
.cardwright-card.json              应用维护：卡片信封（元数据与未知字段）
正则/<序号>-<名称>.html + .json    替换内容 + 参数
脚本/<序号>-<名称>.js + .json      代码 + 参数
开场白/<序号>-<名称>.md            开场白；群聊专用的放 开场白/群聊/
```

- 正文与参数分开，是因为一条人物条目有两三千字、一个前端正则有二十多万字符：放进 JSON 就要逐字转义，改一次就可能毁掉整张卡。
- 文件名里的数字是 `order`，方便按提示词顺序浏览；改文件名不影响 uid。
- 卡内独有、独立世界书表达不了的字段（例如 `use_regex` 不为 `true`、别的工具写的未知键）存在参数文件的 `$card` 段里，导出独立世界书时会剥掉。

## 5 导入导出的坑

1. **BOM**：不少卡文件带 UTF-8 BOM，`JSON.parse` 会失败。读文件时先去掉。
2. **数组顺序**：卡里的 `character_book.entries` 数组顺序没有语义，但导入导出要保持一致，方便逐条比对。Cardwright 把顺序记在世界书清单里。
3. **未知字段**：不认识的字段一律原样保留。删掉别人的扩展字段，等于悄悄改了别人的卡。
4. **顶层镜像**：导出时按 `data` 刷新卡已有的顶层镜像字段，不给原来没有镜像的卡添字段。
5. **往返验证**：导出后立刻把 JSON 读回来，逐条比对 uid 与正文。拼装检查里的 `export-readback` 就是这件事。

## 6 在真实酒馆里导入和更新（实测）

2026-09-18 用 SillyTavern 1.19.0 + 酒馆助手 4.9.5 + MVU-offline 1.0.1 实测，导入的是制卡工坊导出的验证卡。证据在 `artifacts/card-studio-0.8/stage-4/`。

### 第一次导入

1. 导入文件时，卡带标签就先问「导入标签」（全部导入 / 导入现有 / 不导入）。
2. **第一次打开这个角色时**，会接连问三件事，顺序不固定：
   - 「此角色含有内置正则，你想要启用它们吗？」——选**确定**，否则卡里的正则全部不生效（之后可在扩展栏「正则」里启用）。
   - 「This character has an embedded World/Lorebook. Would you like to import it now?」——这句在中文界面下也是英文。选**是**，内嵌世界书以 `character_book.name` 为名存成世界书文件，并绑定到角色（选否的话，之后用角色面板「更多… → 导入卡内世界书」）。
   - 「角色卡 '…' 中包含酒馆助手可用的嵌入式脚本，是否现在就启用它们?」（酒馆助手自己的弹窗）——选**确认**，否则 MVU、变量结构这些脚本都不运行（之后在「酒馆助手 → 脚本库 → 角色脚本」里启用）。
3. 每个问题对同一个角色只问一次。
4. 绑定名就是 `character_book.name`。制卡工坊导出时让它和 `extensions.world` 一致，所以绑定不会错位。

### 更新一张已经导入的卡

- **不要再次「导入」同一张卡**：会生成新角色（`雾港档案1.png`、`雾港档案2.png`），聊天不会跟过去。
- **用「替换/更新」**：角色面板「更多… → 替换/更新 → 用文件替换」，选新导出的卡（JSON 或 PNG 都行）。实测：还是同一个角色文件，聊天记录保留；卡里的正则、酒馆助手脚本随卡整体替换（之前重复导入的单条正则也一起消失）。装了酒馆助手 4.9.5 时，**已绑定的同名世界书文件也会被新卡的内嵌世界书覆盖**（酒馆助手监听了替换/更新）。没装酒馆助手时，替换后再用「更多… → 导入卡内世界书」，确认覆盖——这一步原地保存，不会解除绑定。
- 这就是制卡工坊导出报告推荐的做法：改了哪一件都导出整卡，然后「替换/更新」。

### 单件导入的实际行为

| 单件 | 酒馆里的行为 | 结论 |
| --- | --- | --- |
| 世界书 JSON | 书名取自**文件名**；同名时问是否覆盖，覆盖会先删掉旧书，**角色的绑定随之解除**（`extensions.world` 变空） | 覆盖后要重新绑定；不同文件名会变成一本新书。优先用整卡替换或「导入卡内世界书」 |
| 正则 JSON | 总是新建一条、分配新 id，要在弹窗里选全局 / 角色 / 预设 | 先删旧的再导入，否则会有两条同名正则同时生效 |
| 酒馆助手脚本 JSON | 总是新建、分配新 id，并且**默认关闭**（酒馆助手 4.9.5 源码） | 先删旧的，导入后手动启用 |
