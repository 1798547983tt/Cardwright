## 一、状态栏

### 1. 它是怎么出现的

正文格式条目在正文里写一个占位符（例如 `<StatusPlaceHolderImpl/>`），状态栏正则匹配这个占位符，把它换成一整段 HTML；酒馆助手把这段 HTML 渲染成 iframe；iframe 里的脚本读 MVU 变量，画出界面。

四个环节各属不同分区：占位符属于正文格式，替换属于正则，变量属于脚本 · 变量结构，界面样式属于风格预设。哪一环缺了就去那一环补，不要在状态栏里凑。

### 2. 必须先等 MVU

```js
await waitGlobalInitialized('Mvu');
const data = Mvu.getMvuData({ type: 'message', message_id: 'latest' });
render(data.stat_data);
eventOn(Mvu.events.VARIABLE_UPDATE_ENDED, after => render(after.stat_data));
```

不等就读会拿到空对象，界面上会出现一排「未知」。

### 3. 只在最新一楼渲染

```js
if (getCurrentMessageId() !== getLastMessageId()) return;  // 旧楼层直接不画
```

参考卡（Re0）的状态栏在所有命中的楼层都渲染，长对话里明显变慢——这是已知问题，新卡不要重复。

**实测（2026-09-18）**：MVU 会在**每一条** AI 回复末尾追加 `<StatusPlaceHolderImpl/>`，所以状态栏正则不加限制，每一楼都会画一个。两件事要一起做：

1. 状态栏正则设 `maxDepth: 0`。楼层限制只在楼层被渲染时判断，所以它管的是**载入和重新载入聊天**：那时只有最新一楼会画状态栏。
2. 聊天进行中，旧楼层不会重画，上一楼的状态栏会一直留着。所以状态栏脚本自己判断「我是不是最新一楼」，并在新消息到来时把自己收起来：

```js
const mine = getCurrentMessageId();
const hideIfOld = () => { if (mine !== getLastMessageId()) document.body.replaceChildren(); };
hideIfOld();
disposers.push(eventOn(tavern_events.MESSAGE_RECEIVED, hideIfOld), eventOn(tavern_events.MESSAGE_SENT, hideIfOld));
```

### 4. 显示规则

- 只显示变量表里有的字段；缺失显示「未知」，不要报错、不要补造。
- 数值带范围（`62 / 100`），枚举显示中文名，记录类只显示最近几条。
- 默认折叠成一行关键信息，展开后分区或分页；展开状态可以记在 `chat` 或 `message` 作用域的变量里，但不要写进 MVU 的 `stat_data`。
- 手机宽度下单列，不横向滚动。

### 5. 骨架状态栏（Cardwright 1.1.0）

从 1.1.0 起，状态栏默认由应用自带的前端骨架编译：分区 AI 只写装配单，声明显示哪些变量、分几页、每页放哪些区块。上面第 2、3 节的事由骨架的运行时代劳：等 MVU（带超时）、读 `stat_data`、在 `VARIABLE_UPDATE_ENDED` 后重画、只在最新一楼渲染并在新消息到来时把旧楼层的自己收起、切换聊天时清理全部事件监听、出错时显示错误面板与【复制报错】。三种形态共用同一套渲染：

- **placeholder**：占位符换成一个 iframe，每楼一个，只在最新一楼画出来；正则仍要设 `maxDepth: 0`，拼装检查会核对。
- **header**（默认）：状态栏画在正文美化每一楼的顶部，只在最新一楼展开；状态栏正则只负责删掉占位符，正文美化的装配单要开 `状态头: true`。
- **floating**：应用合成一个酒馆助手脚本，在酒馆页面上挂一个悬浮球和面板（Shadow DOM 隔离，可拖动并记住位置），全局只有一个实例，不占楼层；状态栏正则同样只删占位符。

手写的状态栏（例如导入的卡）仍按第 2、3 节自己做。

## 二、开局页与创角页

### 1. 三种开局

| 形态 | 生命周期 | 适合什么 |
| --- | --- | --- |
| 普通 `first_mes` | 一条真实的开场消息 | 绝大多数卡 |
| 备选开场 `alternate_greetings` | 首条消息的候选 | 不同时间、处境、视角 |
| 创角页 | 一次性的初始化向导 | 需要玩家先定身份、属性、关系的卡 |

三选一的依据是职责，不是界面大小。只是想要三个固定开场，就写三条备选开场，不要做一整套创角页。

### 2. 首条消息是真消息

`first_mes` 会成为聊天里真实的第一条 assistant 消息：它参与上下文、会被 Markdown 渲染、会被正则处理、能被编辑和 Swipe。所以：

- 有正文格式的卡，开场白要按正文格式写，这样第一条消息就能被正文美化接住。
- 创角开场只放 `<start>` 块和一句说明，具体界面由创角页正则渲染。
- 给模型看的内容要短而稳定；不要把整页 HTML 送进模型。可见层与送模层用两条正则分开（一条只改显示，一条只改提示词）——具体顺序与 `markdownOnly` 行为属版本敏感项，必须在真实酒馆里实测。

### 3. 备选开场之间要自洽

每条备选开场都要能直接开始游玩，并且：角色与玩家身份一致、世界状态不互斥、变量初始化的假设相同、常驻世界书条目能解释这个场景。真正不同的世界规则要在提交时写进变量或世界书，而不是只在文字里暗示。

### 4. 创角页的提交事务

创角页只有一个提交入口，按顺序做三件事：

1. **写玩家设定**：写进**当前聊天的聊天世界书**（`getChatWorldbookName('current')` / `getOrCreateChatWorldbook('current', name)`），条目为常驻、角色定义前、顺序 100，世界书名为「卡名 · 存档名」，写入前查重名，已存在就更新。酒馆版本不支持聊天世界书时，退回写角色主世界书，并在页面上明确告诉玩家（ADR 0012）。
2. **填开场信息**：填进酒馆输入框并发送；输入框里已有内容时不覆盖，改为复制到剪贴板并提示。
3. **写初始变量**（需要时）：只写变量表里有的字段，值在取值范围内。

草稿与游戏变量要分开：玩家在向导里改来改去的都是草稿，只有提交那一刻才落到世界书和变量里。界面状态（当前第几步、折叠）不要污染业务数据。

1.1.0 起，装配单编译出的创角页由骨架按同一顺序执行这三步：第 1、2 步写入失败时停在错误面板，玩家已填的内容留在页面上，可以重试；第 3 步写不进去只提示，不影响前两步。

### 5. AI 帮写

只走酒馆当前的模型连接（`generateRaw`）。卡里不提供 API Key 输入框，不请求第三方接口。生成失败时把提示留在页面上，让玩家自己填。

**实测（2026-09-18）**：聊天世界书接口在 SillyTavern 1.19.0 + 酒馆助手 4.9.5 可用（写法见 `50-酒馆助手前端基础.md` 第 5 节）；写进聊天世界书、顺序 100、角色定义前的玩家设定，在提示词里紧跟角色世界书顺序 100 的人物条目。楼层限制在流式输出下的表现见 `30-正则与渲染管线.md` 第 3 节（冒烟开着流式输出）。
