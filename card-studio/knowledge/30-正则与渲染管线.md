# 正则与渲染管线

| 适用版本 | 核对日期 | 核对方式 |
| --- | --- | --- |
| SillyTavern 1.19.0 | 2026-09-17 | 逐条对照 `public/scripts/extensions/regex/engine.js` 源码 |
| SillyTavern 1.19.0 + 酒馆助手 4.9.5 | 2026-09-18 | 真实酒馆实测（流式输出开启），证据在 `artifacts/card-studio-0.8/stage-4/` |

对应分区：正则各分区、世界书 · 正文格式、拼装。

本篇只写制卡要用到的部分。仍带「待真机验证」的条目还没在真实酒馆里测过，不要当成事实施工。

## 1. 一条正则有哪些字段

角色卡里的正则存在 `data.extensions.regex_scripts` 数组里，每条是一个对象。制卡工坊把它拆成两个文件：参数 JSON 和替换内容（`.html`）。

| 字段 | 作用 | 制卡工坊的用法 |
| --- | --- | --- |
| `id` | 唯一标识 | 由应用生成，不要改 |
| `scriptName` | 显示名称 | 空名称在酒馆里存不下来 |
| `findRegex` | `/模式/标志` 字符串 | 为空则整条不执行 |
| `replaceString` | 替换内容 | 就是那个 `.html` 文件；支持 `$1`、`$<name>` 和 `{{match}}`（内部转成 `$0`） |
| `placement` | 作用域数组 | 见下表；空数组等于永不自动触发 |
| `disabled` | 关闭 | 关闭后仍可被斜杠命令手动调用 |
| `markdownOnly` | 只改显示 | 界面里叫 Alter Chat Display |
| `promptOnly` | 只改提示词 | 界面里叫 Alter Outgoing Prompt |
| `runOnEdit` | 编辑消息时也跑 | 只改提示词的正则要设 true |
| `substituteRegex` | `findRegex` 里的宏怎么处理 | `0` 不替换（默认）、`1` 原样插入（危险）、`2` 转义后插入 |
| `minDepth` / `maxDepth` | 楼层范围 | `null` 为不限；深度 0 是最新一楼，数字越大越旧 |
| `trimStrings` | 从捕获组的值里删掉的字符串 | 作用在 `$1`、`$2` 的值上，不是最终结果；不用时留空数组 |

## 2. placement 取值

| 值 | 含义 | 说明 |
| --- | --- | --- |
| 0 | MD_DISPLAY | 源码标注为 deprecated，不要用 |
| 1 | USER_INPUT | 用户发送的消息 |
| 2 | AI_OUTPUT | AI 的回复。前端渲染一律用它 |
| 3 | SLASH_COMMAND | 斜杠命令的返回值 |
| 5 | WORLD_INFO | 世界书注入。**必须同时 `promptOnly: true`**，否则这条路径上不会激活 |
| 6 | REASONING | 推理块（部分模型） |

（4 是历史上的 sendAs，源码里只剩注释。）

## 3. 一条正则什么时候会跑

源码里的判断顺序是：**先看三态，再看编辑，再看楼层深度，最后才看 placement**。四关全过才执行。

三态条件（原样引自源码逻辑）：

```
(markdownOnly && isMarkdown) || (promptOnly && isPrompt) || (!markdownOnly && !promptOnly && !isMarkdown && !isPrompt)
```

由此得到四种组合：

| markdownOnly | promptOnly | 含义 |
| --- | --- | --- |
| false | false | 永久改写聊天记录，显示和提示词都变 |
| **true** | false | **只改显示**：前端渲染用这一种 |
| false | **true** | **只改提示词**：历史裁剪用这一种 |
| true | true | 显示和提示词都改，但不落盘（待真机验证） |

深度过滤：`depth < minDepth` 跳过，`depth > maxDepth` 跳过；`minDepth` 要 ≥ -1、`maxDepth` 要 ≥ 0 才参与判断。所以：

- 只渲染最新一楼：`maxDepth: 0`。
- 只渲染最近 10 楼：`maxDepth: 9`。
- 只处理第 6 楼以深（常见于提示词裁剪）：`minDepth: 6`。
- `minDepth: null` 与 `minDepth: 0` 实际都等于不限下限。

**实测（2026-09-18）：楼层限制只在楼层被渲染的那一刻判断。** 新回复到来时，旧楼层不会重画，所以聊天进行中，每一楼都保持它作为最新楼时画出的样子；重新载入聊天、切换回这个聊天时，才按当时的深度重画。验证卡的正文美化设 `maxDepth: 1`，五轮对话后：

- 进行中：五条回复全部是美化后的样子；
- 重新载入后：只有最新一条是美化后的样子，更早的都是未美化的文字。

所以 `maxDepth` 管得住的是**载入长聊天时**的渲染量——这正是卡变慢的地方。要在聊天进行中也只留最新一楼（例如状态栏），光靠正则不够，前端脚本要自己判断是不是最新楼，并在新消息到来时隐藏自己。

> 待真机验证：Continue 追加消息时的深度计算。

## 4. 多条正则的先后

同一段文本会依次经过所有命中的脚本，上一条的输出是下一条的输入。顺序是**全局脚本 → 预设脚本 → 角色卡内的脚本**（1.19.0 源码 `extensions/regex/engine.js` 里 `SCRIPT_TYPES` 的顺序：`GLOBAL`、`PRESET`、`SCOPED`）——卡里的正则最后跑，看到的是玩家的全局正则和预设正则处理过的文本。角色卡内部按数组顺序执行——也就是制卡工坊里 `正则/` 的序号顺序。

「只改显示」「只改提示词」都不勾的正则，在回复到达时就改写聊天记录本身（这时不看楼层范围）；勾了「只改显示」的，在每次渲染这一楼时再跑。所以一条回复先经过前一类，再经过后一类。

两步式渲染（先插占位符、再把占位符换成组件）依赖这个顺序，序号不要随意调换。

## 5. 显示层的处理顺序

一条 AI 回复到达界面前，大致经过：

```
模型原文
  → 回复到达时：两个「只」都不勾的正则改写聊天记录本身
  → 每次渲染：只改显示的正则（markdownOnly，按这一楼的深度判断楼层范围，此时还没转 Markdown）
  → 引号包进 <q>（跳过 <style> 和代码块）
  → Markdown 渲染
  → DOMPurify 净化（<style> 会被特殊处理，class 会被加前缀）
  → 插入消息 DOM → 酒馆助手把文字里含 html>、<head> 或 <body 的代码块渲染成 iframe
```

据此得出几条制卡规则：

- 替换内容里写完整 HTML 文档最稳妥：交给酒馆助手渲染成 iframe，就绕开了 Markdown 和净化带来的差异。
- 正则跑在 Markdown 转换之前，所以模式要按模型原文写，不要按界面上看到的 HTML 写。
- 宏（`{{user}}`、`{{getvar::}}` 等）在更早的阶段就已经求值完毕，正则看到的是求值后的文本。

**不用 iframe、直接插进消息的替换内容，实测（1.19.0）会被这样改动：**

- **class 加前缀**：`class="cw-update"` 变成 `class="custom-cw-update"`。`data-*` 属性原样保留。
- **同一段替换内容里的 `<style>` 会跟着改写**：`.cw-update summary { … }` 被改成 `.mes_text .custom-cw-update summary { … }`，样式照常生效。所以在替换内容自己的 `<style>` 里照常写类名即可。
- **别处的选择器不会改写**：全局美化 CSS、脚本里的 `querySelector('.cw-update')` 都找不到它——要么写 `.custom-cw-update`，要么用 `[data-…]` 属性选择。
- **引号会被包进 `<q>`**：「……」和 "……" 括起的文字会被包成 `<q>`，显示成酒馆的对白颜色。连 `<pre>` 里的 JSON 也会这样（`<q>"op"</q>`）；要显示原样的 JSON，给 `q` 去掉颜色和引号装饰，或者别直接展示原始 JSON。
- **认识的 HTML 标签保留，不认识的去掉**：`<time>` 保留；`<now_plot>` 这类自定义标签被去掉，里面的文字保留。

> 核对（2026-09-18）：上面的顺序已按 SillyTavern 1.19.0 源码（`public/script.js` 的 `messageFormatting`、`public/scripts/extensions/regex/engine.js`）和酒馆助手 4.9.5（`src/util/is_frontend.ts`）逐段核对；改动方式在 1.19.0 实测。制卡工坊的本地预览按同样的顺序渲染，只是不含玩家的全局与预设正则、不联网、没有酒馆助手的函数。

## 6. 制卡常见的坑

1. `placement: []` 等于这条正则永远不自动触发。
2. 世界书正则（placement 5）忘了 `promptOnly: true` → 整条不生效。
3. 流式输出要两条正则：未闭合的一条（用负向前瞻 `(?![\s\S]*<\/标签>)`）和闭合的一条（用惰性匹配 `[\s\S]*?`）。只写一条会在生成过程中或生成完成后显示异常。
4. `substituteRegex: 1` 会把宏的值原样塞进模式里，角色名带括号或点号就会让模式报错；要动态嵌入就用 `2`。
5. `trimStrings` 只作用于捕获组的值；替换内容里没有 `$1` 时它不起作用。
6. `markdownOnly: true` 的替换结果不会写回聊天记录，所以模型在下一轮看不到它——这正是前端渲染要的效果。
7. 正则匹配的是模型原文，所以正文格式条目里的示例输出就是最好的测试样本；拼装检查也用它来验证命中。
8. 固定件「只发送最新 3 楼的变量更新」（`promptOnly`、`minDepth: 6`）实测有效：第五轮请求里，最早一条回复（深度 7）的更新块被去掉，最近三条保留。
9. 导入单条正则**总是新建一条**（新 id），不会替换同名或同 id 的正则；导入时要在弹窗里选「全局 / 角色 / 预设」。要替换，先删旧的再导入，或者直接用整卡「替换/更新」（见 `10-角色卡格式与导入导出.md` 第 6 节）。

## 7. 与拼装检查的关系

制卡工坊的拼装检查会：编译 `findRegex`（编译失败是错误）、核对 `placement` 取值、检查 placement 5 与 `promptOnly` 的搭配、用正文格式的示例输出验证正文类正则能否命中。检查通过不等于渲染好看，真实效果仍要在酒馆里看。

前端还有两组确定性检查，都按导出后的 `replaceString` 判断：

- **前端围栏**（`frontend-fence`，错误）：完整 HTML 文档由应用包上 ```` ```html ```` 与闭合围栏；文档前后多了文字、内联回执被包了围栏、围栏里的文档不以 `</html>` 结尾、非文档却带 `<script>`，都会报错。
- **前端质量检查**（`frontend-*`）：只查三类 iframe 前端的文档。错误——375px 下会横向滚动（比 375px 宽的固定宽度、没有横向滚动容器的七列以上表格）、整个前端没有任何交互反馈（没有 `:hover`/`:active`/`:focus` 也没有事件监听）、`:root` 里正文色与底色（或面板色）对比度低于 4.5:1、用了 Google Fonts、以 base64 塞进 16 KB 以上的大文件。警告——设计令牌少于 12 个、没有任何 `@media`、有循环动画却没写 `prefers-reduced-motion`、主强调色 `var()` 用了 8 处以上。
