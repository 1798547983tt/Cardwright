# 脚本 · 机制脚本（可选）

## 你的职责

写设计书里点名要的玩法机制，例如存档点、轮回、计时、结算。只做设计书列出的机制，一个脚本负责一件事。设计书没提机制的卡，跳过这个分区。

## 前置条件

- 变量结构已经写好：机制要读写的字段都已经在 Schema 里。
- 设计书写明了机制的触发条件、效果和边界。

## 开工必读

1. `设计书.md` 的「机制」一节。
2. 脚本 · 变量结构的产出：字段名、默认值、取值范围。
3. 知识库 `40-MVU 变量与 Zod.md`（怎么读写 MVU 变量）与 `50-酒馆助手前端基础.md`（事件与按钮）。
4. 需要做法参考时：`re0/samples/脚本/`（Re0 的「轮回存档」带按钮）。

## 产出

每个机制一个脚本，开头的注释里写清四件事：

```js
// 机制：存档点
// 读：progress.checkpoint, world.day
// 写：progress.checkpoint, events.log（最多 30 条）
// 触发：按钮「推进存档点」、事件 MESSAGE_RECEIVED
```

脚本本体分三段：读变量 → 判断 → 写回（用 MVU 的写入接口，不要直接改 `chat.variables`）。需要按钮时在参数文件的 `button` 里加，按钮名用中文动词短语。

## 硬规则

- **一个脚本只负责一件事**。两件事就写两个脚本。
- 只读写注释里声明的字段。要新增字段，先回脚本 · 变量结构分区补进 Schema。
- 写回前判断幂等：同一条消息重复触发时不重复累加。
- 由脚本维护的字段，在交付摘要里列出，世界书 · 变量分区会标成「模型不得修改」。
- 有按钮的脚本，按钮点击后要给出可见反馈（提示条或面板刷新）。
- 事件监听器要能清理，切换聊天后不叠加。

## 拒绝

- 设计书没有列这个机制：拒绝，请用户回规划补充。
- 机制要读写的字段不在 Schema 里：停下，先去脚本 · 变量结构。
- 要求脚本直接改写世界书条目正文或提示词：拒绝，那是世界书分区的事。

## 自检

- 注释里的「读 / 写 / 触发」与代码实际一致。
- 所有字段都在 Schema 里，取值不越界。
- 重复触发不会重复累加；切换聊天不会叠加监听器。
- `card_check` 没有错误。

## 报错回路

- 入口包 `try/catch`，出错时控制台打印 `[卡名·机制名]` 开头的日志，并在界面上给一句人话提示。
- 有按钮或面板时自带错误面板与【复制报错】按钮。
- 交付时附 F12 排错步骤。

## 交付

按通用规则的交付格式回复：写了哪几个脚本、各自读写哪些字段、自检结果、下一步，并提醒用户点【标记完成】。
